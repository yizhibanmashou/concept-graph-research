# 紧凑别名表示与完整分支预算：事后试点

在观察原始 JSON 的候选预算损失后，探索用候选内部短别名代替反复出现的长义项 ID。目标 ID 由候选检索系统在模型输入外保留；每个选中依赖按原 ID 排序分配 `d0`、`d1` 等别名，依赖清单中同时保留别名及其完整 gloss。B 为依赖清单；C 为同一批依赖节点在任一完整 AND 分支中共同出现所形成的**简单无向 2-section**：对每个分支枚举节点对，跨分支合并重复边，不编码方向、角色、频次或目标到依赖的边；D 保留完整 AND 分支及其 OR 分组。因而 C 明确丢失分支划分，D 保留该高阶结构。候选检索系统仍在模型输入外保存目标 ID、原始记录和别名映射；不同候选的别名只在各自内部有意义，不是跨候选共享的语义身份。

在同一 40 个探索目标、同一 BERT 词表和 128/256/512 候选 token 门槛下，沿用原分支顺序贪心选择整条分支：只有 A/B/C/D 的新序列化均在预算内才接受。与旧长 ID JSON 方案报告全部／部分／零分支保留目标数及保留分支总数；不存在上下文拼接、模型准确率或语义质量测量。两种表示包含相同已选依赖及分支结构，但文本表面形式不同；并未证明两者对编码器等价。观察开发试验后提出方案，属于事后方法探索，不能称独立验证或最优方法。

## C 条件对照语义审计（2026-10-31）

代码审阅发现旧 `representations()` 的 C 字段只是再次列出所有 dependency alias，没有任何节点对或邻接关系；因此旧 C 不构成“普通成对依赖图”，其 packing 输出不能用于评估 pairwise 条件覆盖。历史文件保留为原始记录，不覆盖或重标。

现修订 C 为分支内依赖节点的无向 2-section，边按无序节点对去重。合成反例验证：一个 `{a,b,c}` 的 AND 分支与三个 `{a,b}`、`{a,c}`、`{b,c}` 的 AND 分支拥有相同 C 边集合，但 D 分支划分不同。这明确了 C 与 D 的处理差异：C 保留局部两两共现，D 额外保留哪些条件联合满足。C 序列变长可能影响共同预算下可保留分支数，因此任何后续准备数据都必须报告原始/保留分支和各条件 token 数；旧的 40 项 packing 结果不代表新 C 的覆盖。

这只是设计与合成性质核验，不是对 C 本体选择的科学确认，也没有重生成 SemCor 数据、重训或读取开发/测试标签。新性能实验启动前，须由负责人审定 C 的 2-section 定义，固定分支共用预算及可评分分母，并取得独立来源的开发评估集；不得用已反复设计的旧 dev 选择阈值或预算。
